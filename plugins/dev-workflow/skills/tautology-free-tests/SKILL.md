# トートロジーテストをやめる

**green であることは、何かを確かめた証拠ではない。**

このスキルは「テストが通った」と「テストが判定を要求している」を区別するためのもの。
複数の PR を並行して進めた実装で実際に踏んだトートロジーの型と、検出に使った測り方をまとめる。

## 中心の問い

新しい検査を書くとき、既存の検査を読むとき、次の問いを立てる。

> **この検査が発火しなかったら、何が壊れていたか。**

答えが「何も壊れない (別の機構が同じ箇所を名指して落とす)」なら、その検査は要らない。
答えが出てこないなら、まだ何を守るのか決まっていない。

そして検査の値打ちを発火回数で測らない。発火回数は、その検査自身が作ったずれを数えているだけのことがある。

## 測り方

トートロジーは読んでも分からない。動かして測る。

### 1. 判定を潰して、落ちない数を数える

判定関数を `return ()` / `return None` に差し替えて全件実行する。

```
32 件中 21 件が落ちた (failures=1 / errors=20)
残る 11 件は「違反なし」を期待するケースで、空の判定でも通る
```

落ちない件数が、判定の存在を要求していないテストの数になる。

次の点に注意する。

- 落ちないテストが無駄とは限らない。「違反なし」を期待するケースは false positive を止める側なので、
  判定を潰しても落ちないのが正しい。測っているのは「このテストが判定の存在を要求しているか」で、価値ではない
- 赤が出た理由を確かめる。例外で落ちたもの (errors) は、判定を差し替えたつもりが、
  その手前の import で落ちていることがある

### 2. 守りたい欠陥を、実際に仕込む

「この検査は X を防ぐ」と書くなら、X を作って落ちることを見る。

```
rules/__init__.py から rule_13 の 1 行を消す
  スイート全体                   全件 OK              ← 落ちない
  テストを経由しない別プロセス   in registry: False   ← 欠陥は実在
```

仕込んで通るなら、その検査は X を防いでいない。

### 3. 分母と分子を分ける

「N 回拾った」だけを報告しない。実行した回数と、食い違った回数を分ける。
次の例は、型 1 の件数の pin を並行作業の中で実測した結果になる。

```
実測を実行した       7 回
実際に食い違った     5 回
ずれていないと確認   2 回
git の表示に出た     0 回
```

実行して何も出ない回があるのは、検査として正常な結果になる。
分子だけを数えると、次はその数を過大に数える誘因が生まれる。

## 型

### 1. 自分が作ったずれだけを拾う件数の pin

```python
self.assertEqual(len(registry.all_rules()), 36)
self.assertEqual(len(planned), 11)
```

守るつもりだったのは「ルールの一覧表 (カタログ) に載った全ルールが、レジストリに登録されている」こと。
カタログとレジストリのずれ (drift) を拾うための検査だった。
`planned` は、カタログに載っているがまだ実装していないルールの一覧を指す。
ところが 7 回実行して 5 回食い違い、食い違いはすべて並行 PR の衝突から来ていた。本当の drift は 0 件。

しかも並行する PR どうしが同じ行を同じ値へ書き換えると、git は 1 回分しか適用しない。
このとき conflict は起きず、`dropping ... already upstream` の表示も出ない。
`git status` にファイルが現れないこともあり、実測でしか捕まえられない。

> 総数を固定する検査は、並行作業では衝突だけを生む。

### 2. 対象が空でも通る `assertTrue(executed)`

```
roots=[] executed=12 findings=0
```

対象のディレクトリ (`roots`) が空でも、実行したルールの数 (`executed`) は 12 になり、検出 (`findings`) は 0 件になる。
fixture を使った場合と出力が同じになる。「実行された」は「判定された」ではない。

### 3. 主張したいものを見ていない部分文字列の `assertIn`

```python
self.assertIn("mylint check", hook["entry"])
```

確かめたかったのは「pre-commit の hook が CI と同じコマンドを実行する」ことだが、
`--strict` のような引数の有無を見ていない。CI 側のコマンドが変わっても落ちない。

正しい形は、CI 側の定義からコマンドを読み出して突き合わせること。

```python
ci_command = load_ci_step("lint")["run"]   # CI の workflow 定義から読む
self.assertEqual(hook["entry"], ci_command)
```

### 4. import の副作用によるマスク

`unittest discover` は全テストモジュールを import する。
`tests/test_<id>.py` の先頭が `from ...rules.<id> import check` なら、
その import が登録処理を実行するので、登録漏れが検出できない。

ルールを足す手順が「ルールごとにテストファイルを書く」と決めているなら、
手順どおりに実装した人は必ずこのマスクを作る。
検査を書く前に、その検査が依存している副作用を数えること。
この例では、`rules/__init__.py` を `ast` で読んで登録している ID を取り出す形にすれば、import の副作用に依存しない。

### 5. fixture が前提を満たさず、主張が空振り

「全ルールが停止する」を主張するテストで、fixture が git リポジトリでなかったため
テストが最初に呼んだルールが例外を投げ、残りのルールについては何も確かめていなかった。
それでもテストは green のまま通っていた。

この型は後から現れる。素の一時ディレクトリを fixture にしていた間は、
git に尋ねてパスを判定するルールが無かったので、前提の欠けた fixture でもテストは意図どおりに通っていた。
前提を要求するルールが加わった時点で、既存のテストが空振りへ変わる。

したがって「fixture が前提を満たしているか」は、fixture を書いた時点では判定できない。
判定の種類を増やす変更を入れるときに、その前提を満たしていない fixture が既に無いかを見る側の作業になる。

なお、この空振りに後から気づけたのは、そのルールが「git に尋ねられなかった」ときに黙って空を返さず、
raise していたからになる。
「何も無かった」と「調べられなかった」は結論が逆なので、混ぜないこと。

### 6. 対象範囲が広すぎる assertion

```python
self.assertNotIn("planned", text)   # 出力全体に当てていた
```

判定したいのは「要約行に未実装 (planned) のルールの件数が出ていないこと」なのに、見ていたのは
「本文のどこにも語が無いこと」。直し方の案内文に同じ語が入っただけで落ちる。

> `assertNotIn` / 部分文字列 / 正規表現を書くときは、「何が入ってきたら落ちるか」を先に言う。
> 言えないなら対象範囲が決まっていない。

同族の問題として、位置を部分文字列で探すと先勝ちマッチが起きる。
部分文字列を含む最初の行の番号を返す helper `_line(file, "dev:")` が、`dev:` より前にある `pre-dev:` の行を拾う。
行番号が違反の同一性判定に入っていると、位置の誤りが検出の欠落へ変わる
(別々の 2 件が同じ違反とみなされ、1 件消える)。位置は parser から取る (`yaml.compose` の `start_mark` など)。

### 7. 計算したのに使っていない値

```python
env_name = config_path.stem   # F841: assigned but never used
```

実データから計算したローカル変数は、何かのために計算している。
使っていないなら、続くはずだった突合が書かれていない。

対して、未使用の import は信号が弱い。型注釈のパターンごと写されて残ることがある。
未使用のローカル変数と未使用の import を混ぜないこと。

ただし、未使用のローカル変数が言うのは「ここには書かれていない」であって、「どこにも書かれていない」ではない。

実例では、同じ突合を既存の別のルールがより広い対象範囲で既に行っていた。
テストが照合しようとしていたのは 1 つの環境の設定だけだったが、そのルールは全環境の設定を、
環境変数による上書きまで含めて照合していた。その突合を足していれば、狭くて弱い写しが 1 つ増えていた。

> 探す範囲に隣のツールを入れる。同じディレクトリと同じテストファイルだけ見て「無い」と判断しない。
> 判定は別の層に載っていることがある。

そして測り方 2 で確かめる。欠陥を仕込んで、何がどう落ちるかを読む。
「落ちるが 1 段遠い」と「落ちて、宣言の行を名指す」は違う。前者なら足す価値があり、
後者なら足すと二重になる。

### 8. 読み手が実際に従う欄を見ていない

エラーの `message` だけを assert して、`remediation` (読み手が実際に従う直し方の指示) を見ていなかった。
例に取るのは、既知の違反を一時的に許す例外リストを検査するルール。
このルールは性質の違う状況をまとめて報告するのに、remediation は「エントリを削除してください」の 1 文しか持てなかった。
次の状況では、従うほど状態が悪くなる。

- 例外リストに書いた件数が実際の違反より多い → エントリの削除ではなく件数の訂正が要る
- 違反かどうかをそもそも判定できていない → 削除すると、正当な例外まで消える

どちらの状況でも、remediation に従った読み手が例外リストを誤った状態へ変える。

unit test は通っていた。実物を実行して初めて出た。

型 3 (部分文字列の `assertIn`) の変種に見えるが、別物になる。
型 3 はどう照合するかの誤りで、この型はどの欄を見るかの選び違いになる。

> 出力に複数の欄があるなら、読み手が行動の根拠にする欄を assert する。
> 判定が正しいことと、指示が正しいことは別に確かめる。

### 9. 「0 件でした」だけの報告

0 件が空虚でないことを示す。

- 分母を出す (重複した設定 key を探した例なら `走査したファイル 30 / 読んだ定義 600 / 重複を除いた後 600 / 重複した key 0`)
- 植え込んで答えが変わることを見せる
- 「対象が無い」と「対象が現れたときに動く」を分ける

> 「重複を除いてみたが何も変わらなかった」と「重複がまだ 1 件も現れていない」は別のことを言っている。

## 検査を足す提案をするとき

「置き換えを足さない」が正解のことがある。

ある件数の pin を廃止するにあたり、代わりの検査の案が出た。
どの案も、廃止する pin が守るはずだったものを守れていなかった。

| 案 | なぜ守らないか |
| --- | --- |
| ID の重複が無い | `register` が二重登録で例外。assertion まで到達しない |
| 実装と planned が交差しない | `register` が二重登録で例外。assertion まで到達しない |
| カタログの ID 一覧と集合比較 | 複製がそのまま新しい pin になる |
| registry と rules ディレクトリのファイル一覧の突合 | テストの import が登録を実行してマスクされる |

検査を書くという行為は、書いた人にも守っているかどうかを見せない。
提案する側と受ける側の双方が、測り方 2 (欠陥を仕込む) を通すまで信じないこと。

そして機構を消すなら、消えたことを沈黙で表さない。
「この drift を今は機械が見ていない。唯一の経路は X である」と書き残す。

## 実測の作法

トートロジーの検出は実測に依存する。その実測にも条件がある。
実測の結果を別の作業者やエージェントへ渡すときと、受け取るときに次を守る。

- 再現しない実測は実測ではない。渡す前に最低 1 回再現する
- 再現は「2 回測る」ことではない。2 回目を 1 回目と同じ地点から始めることを指す
  (`git merge --abort` と `git reset --hard` の両方を挟む)。
  同じ作業ツリーで続けて読むと、1 回目が作った状態の上で 2 回目を読む
- 渡された数字は答え合わせに使い、導出の入力に使わない。
  引き算が合っていても、渡された分母が古ければ答えは狂う
- 数字を渡す側は「何を測ったか」を添える。構成が違えば別のものを測っている
- 予想値を配るときは、答え合わせ用であって導出の入力ではないと明示する。
  添えなければ入力として使われ、正しい値を「直させて」壊す

## 削る側の作法

トートロジーを消すと、そこに書かれていた情報も消える。
削る前に移し先を名指す。候補は次の表のとおりで、探す順はテストが先になる。

| 置き場所 | 誰のためか |
| --- | --- |
| テスト | 読まれなくても効く。まず既にそこに無いか探す |
| docstring | コードを読む人 |
| commit message | 後から履歴を掘る人 |
| 本文 / 説明文 | いま読む人 |

「テストへ移そう」ではなく「移し先を探す段階でテストを見る」。
前者は新しく書く話で、手間が大きい。後者では既にあるかもしれないものを先に確かめるので、手間が小さい。

**移し先が無いなら、削らない。**
