# skill の文言の書き方

skill の中身を説明する文は、skill 本文の 1 か所にだけ置く。ほかの置き場の文言は、その本文の所在を指す。

## 置き場ごとの文言

| 置き場 | 文言 |
|---|---|
| hook の deny 文言 | 「`<形>` は使いません。<skill 名> skill に従ってください。」の 1 文 |
| skill の description | 主題と引くきっかけ ([SKILL.md](SKILL.md) の description の節) |
| 他 skill や CLAUDE.md からの参照 | skill 名と、その場で必須かどうか |
| skill 本文 | 手順・診断・判断の基準と、それを支える機序 |

deny 文言と参照行は、たとえば次の形になる。

```text
PATH に /nix/store のパスを手で足す形は使いません。my-plugin:resolving-path skill に従ってください。
```

```markdown
- `.envrc` を書くときは my-plugin:resolving-path skill に従う (必須)。
```

既存 skill に用途を 1 つ足すときは、本文の表か節に 1 行を足す。description・参照行・deny 文言は
そのまま残す。

## 本文の並び

本文は、エージェントがその場で取る行動の順に並べる。

1. skill が何を扱うかを 1〜2 文
2. 症状から行動を引く表、または判断の分岐
3. 手順と、推奨する形の例
4. 推奨しない形と、それを見つけたときの置き換え先
5. APPENDIX: 機序 (なぜその手順・形になるか)

2 は、description の引くきっかけに症状が含まれる skill だけが持つ。持たない skill は 1 から 3 へ進む。

手順の各段は、その段で実行するコマンドと、出力をどう読むかだけを持つ。なぜそうなるかを知りたくなる
箇所は、APPENDIX の見出しを 1 行で指す。APPENDIX に置くのは、手順か形を変える理由だけにする。

見出しと手順は「正しく使う」側から書く。「〜を止められたとき」「〜が壊れたとき」を見出しにせず、
その作業そのもの (「ファイルを書き換える」「ジョブを足す」) を見出しにする。症状は、上の並びの 2 にある表で
行動に結びつける。

範囲を表す語 (「全部」「すべて」「常に」) は、実際にそうなっているときだけ使う。一部なら、
その一部の条件を書く。

## 決めごとの置き場

決めごとは、その判断を下す skill に書く。skill を読ませずに起動した subagent (baseline) が
その判断の場面で最初に引いた skill を、書き込み先の候補とする。運用の手順を持つ skill ではなく、
判断そのものを持つ skill に寄せる。たとえば issue の起票先の判断は `my-plugin:filing-issues` に置き、
issue の運用の手順を持つ skill には置かない。

## APPENDIX: なぜこの形にするか

同じ説明を deny 文言・description・参照行・本文に写すと、変えるたびに全部を直すことになり、
直し漏れた箇所が古い説明を言い続ける。description は全 skill ぶんが毎セッション読み込まれ、
その一覧には上限がある。長い description は、他の skill の引くきっかけを一覧から押し出す。

背景から入る本文は読み飛ばされやすく、エージェントは description だけで判断しがちになる。手順の途中に
挟んだ機序の説明も読み飛ばされやすく、手順の段を探す手間だけが増える。

症状を見出しにすると、その症状に当たったときにしか節が引かれない。作業を見出しにすれば、症状が出る前の
作業でも同じ節が引かれ、症状を避ける形で書ける。

決めごとを運用側の skill に置くと、判断の場面で引かれた skill には決めごとが無く、エージェントは
決めごとを知らないまま判断する。
