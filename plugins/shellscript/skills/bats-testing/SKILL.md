# bats-core シェルスクリプトテストガイド

bats-core によるシェルスクリプトの単体テストの書き方を扱う。

## テストを書くかどうかの判断

bats は「スクリプトを実際に走らせて、入力に対する出力・終了ステータス・副作用を
確かめる」ためのもの。この形にならないものはテストにしない。

### 書く

| 対象 | 例 |
| ---- | -- |
| スクリプトの振る舞い | hook に JSON を食わせて deny/allow と exit code を見る |
| 生成ツールの入出力 | fixture を入力に与えて生成結果を比較する |
| 生成物のドリフト | `--check` を 1 本。pre-commit が走らない CI 側の担保 |
| 黙って壊れる不変条件 | 設定ミスがエラーにならず機能だけ死ぬもの (後述) |

### 書かない

- **対象コードを実行しないテスト**。テストの中で `ln -sfn` や `mv` を再現してから
  結果を確認するものは、標準コマンドを検証しているだけで、対象を壊しても落ちない。
  再現したくなったら、そのロジックをスクリプトへ切り出して呼ぶ。
- **設定値の写経**。`jq` で設定を読んで期待値と比べるテストは、設定を編集した人が
  同じ値をテストへ書き写すだけになる。差分レビューが見るものと変わらない。
- **ドキュメント・プロンプトの文面 grep**。`grep -q 'gh pr merge'` の類は、推敲の
  たびに落ちるが動作は何も担保しない。LLM へ渡すプロンプトは特に該当する。
- **ファイルの存在と frontmatter の確認**。読み込む側が起動時に落ちるか無視するので、
  そちらで気づける。
- **実装ファイルの行を grep する構造テスト**。Taskfile や設定を変えるたびにテストも
  変える二重管理になる。振る舞いとして検証できないなら書かない。

### 例外: 黙って壊れる不変条件

設定ミスがエラーにならず、機能だけが動かなくなるものは静的検査で残してよい。
残す条件は次の 2 つ。

1. 実行時に気づく手段が無い (ログにも出ず、起動もしてしまう)
2. なぜ壊れるのかをテストのコメントに書ける

例: legacy の設定キーが 1 つでも残っていると新しい sandbox 設定が無効化される、
socket 許可を隣のキーへ書くと schema エラーにならず無視される、といったもの。
「念のため」で足すと歯止めが無くなるので、実際に踏んだ罠だけを対象にする。

「この語が出てこないこと」という負の assertion の形にすると、対象が増えても
テストの更新が要らない。正しい値を列挙する形は避ける。

### 粒度

入力だけが違う同種のケースは、1 ケース 1 テストにせずループでまとめる。
表示の分岐やフラグの網羅を 1 件ずつ `@test` にすると、カバレッジは増えないまま
テスト数だけが膨らむ。

### 棚卸しのとき

既存テストを消してよいかは「対象コードにバグを入れたとき、このテストは落ちるか」で
判断する。落ちないなら消す。落ちるとしても、意図した変更のたびにテストも一緒に書き換える
運用なら、それも消す。

## クイックリファレンス

### インストールと実行

```bash
# インストール
brew install bats-core

# テスト実行 (ハング時の暴走を防ぐため timeout を付ける)
timeout 60 bats tests/                    # 全テスト
timeout 60 bats tests/my-test.bats        # 特定ファイル
timeout 60 bats --verbose-run tests/      # 詳細出力
```

bats はバックグラウンドで多重に投げない。ハングすると同時にプロセスが積み上がる。

### 基本構文

```bash
#!/usr/bin/env bats

setup() {
  # 各テスト前に実行
  load 'helpers/mock.sh'
  source "$DOTFILE_DIR/script.sh"
}

teardown() {
  # 各テスト後に実行
  cleanup
}

@test "テストの説明" {
  run my_command
  [ "$status" -eq 0 ]
  [[ "$output" == *"expected"* ]]
}
```

### run コマンド

```bash
run my_command arg1 arg2

$status  # 終了ステータス
$output  # 標準出力 + 標準エラー
$lines   # 出力を行ごとに分割した配列
```

`run` は対象をサブシェルで実行するため、グローバル変数の変更は親に反映されない。

### アサーション

```bash
[ "$status" -eq 0 ]                    # 成功
[ "$status" -ne 0 ]                    # 失敗
[[ "$output" == *"substring"* ]]       # 部分一致
[[ "$output" != *"unwanted"* ]]        # 不一致
[ "${#lines[@]}" -eq 5 ]               # 行数
```

## dotfiles での使用箇所

| ファイル | 説明 |
|---------|------|
| `tests/peco-gcop.bats` | peco-gcop 関数のテスト |
| `tests/fixtures/git-setup.sh` | テスト用 Git リポジトリ作成 |
| `tests/helpers/peco-mock.sh` | peco コマンドのモック |
| `tests/helpers/zle-mock.sh` | zsh zle/bindkey のモック |

### ディレクトリ構造

```
tests/
├── *.bats              # メインテストファイル
├── fixtures/           # テスト用データ・セットアップ
└── helpers/            # モック・ヘルパー関数
```

## TDD ワークフロー

```
1. Red: テストを書く → 失敗を確認 → コミット
2. Green: 実装する → テストパス → コミット
3. Refactor: コード改善 → テスト維持
```

## よくある問題

| 問題 | 解決 |
|-----|------|
| `bindkey: command not found` | モックをテスト対象より先に読み込む |
| 変数が変更されない | `run` の代わりに直接実行 |
| `trap: undefined signal: RETURN` | `trap ... EXIT` を使う (bash 互換) |
| モックを置いた途端テストがハングする | 呼び出し回数を数えるモックで本物を `exec` している。aqua shim が PATH を再解決して無限再帰する ([reference.md](reference.md)) |
